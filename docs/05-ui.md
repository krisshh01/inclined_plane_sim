# 05 · Control panel (`ui.c`, `ui.h`)

**Role:** every interactive control: the left panel, the transport bar, keyboard
shortcuts and the scene's mouse zoom and pan. It is the **only** module that
writes `Params` and `ViewOptions`, and the only file that defines
`RAYGUI_IMPLEMENTATION` (so Raygui's code is compiled exactly once).

## Public functions

| Function | What it does |
|---|---|
| `UI_Init()` | sets the Raygui font and applies the colour theme (`ApplyTheme`) |
| `UI_Draw(p, v)` | handles shortcuts, draws the left panel and transport bar, runs button actions. **Returns true if a physical parameter changed** |
| `UI_HandleScene(v, sceneRect)` | mouse wheel zoom (10 % per notch, 0.3×–4×) and drag-to-pan inside the scene |

### How a parameter change is detected

```c
const Params before = *p;
... draw every control (they write into *p) ...
return memcmp(&before, p, sizeof(Params)) != 0;
```

`main` then calls `Sim_SetParams`. This avoids tracking which slider moved.

## Immediate-mode GUI, in short

Raygui has no widget objects or callbacks. Each control is a function called
**every frame** that both draws itself and returns whether it was used. The
"state" is just the variable passed by pointer:

```c
if (GuiButton(rect, "Reset")) Sim_Reset();       // clicked this frame?
GuiSliderBar(rect, NULL, NULL, &p->mass, 0.1f, 20.0f);   // writes p->mass while dragged
```

## The rounded look: Raygui for input, ui.c for drawing

Raygui draws square boxes. To get rounded, shaded controls, `ApplyTheme` makes
Raygui's boxes **fully transparent** for buttons, toggles, sliders, check boxes
and the text box. Raygui still handles the mouse and draws the text, and `ui.c`
draws the visible shapes:

| Helper | Draws |
|---|---|
| `HotState(rect)` | returns `HOT_NONE` / `HOT_HOVER` / `HOT_DOWN` from the mouse, for shading |
| `Surface(rect, fill, border, hot)` | rounded raised surface: lighter on hover, darker when pressed, faint top highlight |
| `Button(rect, text)` | `Surface` underneath, then `GuiButton` on top for the click and the label |
| `ColoredButton(...)` | the Start / Pause / Resume button: solid green or amber, bold dark text, soft glow. It saves and restores the button's text colours because Raygui has no per-call colour argument |
| `DrawSlider(...)` | thin sunken track, accent fill, round knob with shadow; halo on hover |
| `SliderX(...)` | the pixel x of a value on the track, using the same mapping as Raygui, so the knob sits exactly where clicking would put it |
| `CheckRow(x, y, text, &flag)` | rounded box with a drawn tick; the hit area includes the label |
| `DrawCard(rect, title)` | a panel card with a small upper-case title |

Draw order matters. Surfaces are drawn **before** the Raygui call, so Raygui's
text lands on top. The slider and tick are drawn **after**, so they show the
value Raygui just updated.

## Left panel (`DrawLeftPanel`)

1. **Header**: ramp logo, title, subtitle.
2. **PARAMETERS**: six `SliderRow`s: Angle, Mass, Gravity, v0, μs, μk. After
   them, `μk` is clamped to `≤ μs`.
3. **CRITICAL ANGLE**: θc = atan(μs) (large, amber), θk = atan(μk), and a status
   chip:
   - θ > θc → "released from rest, it slides" (amber)
   - θ < θc → "released from rest, it sticks" (green)
   - within 0.05° → "on the verge of sliding"
4. **VECTOR LENGTH**: arrow scales (drawing only, never the physics).
5. **SHOW**: seven check boxes for the `ViewOptions` flags.
6. **Keyboard hints** in small key-caps, wrapping to the panel width.

### `SliderRow`: label | slider | value field, with snapping

```
GuiSliderBar(...)                  Raygui updates *val from the mouse
*val = round(*val / step) * step   snap to the precision shown on screen
clamp to [lo, hi]; turn −0 into +0
draw the value text, the optional amber marker, then the slider
```

| Slider | Range | Step | Shown as |
|---|---|---|---|
| Angle | 0–90 | 0.1 | `30.0°` |
| Mass | 0.1–20 | 0.1 | `5.0 kg` |
| Gravity | 0.5–25 | 0.01 | `9.81 m/s²` |
| v0 | −8–8 | 0.1 | `+0.0 m/s` |
| μs, μk | 0–2 | 0.01 | `0.40` |
| Vector lengths | 0.25–3 | 0.01 | `x1.00` |

**Why snap?** The simulation must use exactly the number on screen. Without
snapping, v0 = −0.04 m/s would display as "−0.0 m/s" while the block actually
starts moving, and below θc (but above θk) kinetic friction can't stop it. The
block would slide even though the panel says it should stick.

### Typing a value (`ValueField`)

The value on the right of every slider row is also a text field:

| Action | Result |
|---|---|
| Click the value | it becomes a text box (deep blue), empty, with the current value as a faint hint |
| Type a number, press Enter (or keypad Enter), or click anywhere else | the value is applied, snapped to the row's step and kept in its range |
| Esc | cancels; the old value stays |

- Only one field is edited at a time. The value being edited is identified by
  its address (`editVal`), and its range and step are stored when editing starts
  (`editLo`, `editHi`, `editStep`), so `CommitEdit()` can apply it from anywhere.
- Clicking another field, a slider or a button first applies the open field.
  The field is processed **before** its own slider, so clicking that slider
  applies the typed value and then lets the slider move: the last action wins.
- A decimal comma is accepted (`9,81`), and trailing text is ignored (`30 deg`).
- **Feedback:** if the number was out of range (clamped to the nearest limit) or
  was not a number (ignored), the field's border flashes amber for about a second.
  The same happens when a typed μk is capped at μs.
- While typing, the keyboard shortcuts are off (so Space or R type nothing into
  the simulation). Esc's normal job of closing the window is also switched off
  (`SetExitKey(KEY_NULL)`), so Esc can cancel. The time box follows the same Esc
  rule.

The Angle slider passes `θc` as a `marker`: an amber notch on the track showing
where sliding starts. The v0 slider passes `0` so its notch marks "no initial
velocity". Sliders without a notch pass `NO_MARKER` (NaN, which is never inside
`[lo, hi]`).

## Transport bar (`DrawTransportBar`)

```
Row 1:  [ Start/Pause/Resume ] [Reset] [Step -] [Step +]   Time [ 1.200 ]
Row 2:  Step size [0.01][0.1][1.0]    [Zoom -] [Zoom +] [Reset view]
```

- **One button for three actions.** Its label and colour follow the clock:
  STOPPED → green "Start", RUNNING → amber "Pause", PAUSED → green "Resume".
- **Step ±** move by the selected step size (`stepSizes[stepSel]`).
- **Time box.** Normally it mirrors `Sim_Time()`. Clicking it clears the text and
  enters edit mode (deep blue with a blue outline). Enter or a click elsewhere
  calls `Sim_JumpTo(atof(text))`. `GuiTextBox` returns true on each of those
  transitions, and the `timeEdit` flag tracks which one it is.
- **Step size** is a `GuiToggleGroup`. The chosen segment is drawn in accent blue.
- **Zoom** multiplies or divides by 1.2, clamped to 0.3–4. **Reset view** sets
  zoom 1 and pan 0.

## Keyboard (`HandleShortcuts`)

| Key | Action |
|---|---|
| Space | Start / Pause / Resume |
| R | Reset |
| ← / → | step back / forward by the step size |

Shortcuts are **ignored while typing in the time box or a value field**, so
typing a number can't trigger them.

## Scene mouse (`UI_HandleScene`)

- Wheel inside the scene: `zoom *= 1.1^notches`, clamped.
- Left-drag that *starts* inside the scene pans, and continues until the button
  is released, even if the mouse leaves the scene.

The scene rectangle excludes the transport bar, so its buttons never pan the
view.
